# 2.11.0 内核与工具优化

本轮对应：增量操作、共享索引、持久化可靠性、AI 请求幂等与字段冲突保护、统一操作契约。时间线仍为 v17，已有工程可直接读取。

## 编辑内核

`applyOps` 改为按操作进行写时复制。未修改的元素和轨道保持原对象引用；失败时丢弃当前操作的草稿，前面的成功操作保持原行为。重复设置相同数值或等价对象返回 `ignored`，不产生新修订。失败创建操作占用的 ID 会释放。

布局只重算受影响的元素和分组；改变全局画布或结构时仍进行必要的全局处理。删除动画前序后的时间修复继续保留。

共享索引记录元素与片段位置、分组成员、素材引用，以及布局/编排是否存在。仅修改数值时复用索引，结构和引用变化后重建。渲染分组也复用成员关系，避免逐帧为每个元素重新扫描整组。

时间线视为不可变数据：调用方应使用 ops 生成新版本，不应直接修改已有对象。草稿对象只在归约器内部存在，最终结果可正常 JSON 序列化及 `structuredClone`。

### 可复现基准

执行 `node tests/bench/kernel.mjs`，默认 2,000 个文字元素、100 次 X 坐标修改，预热后测三次中位数。可用 `BENCH_ELEMENTS` 调整元素数量。

本机记录在 [kernel-2.11.json](benchmarks/kernel-2.11.json)：旧内核 **1,026.73ms**，新内核 **13.31ms**，约 **77 倍**。进程 RSS 采样从 96MB 降至 80MB；这不是峰值内存测量。

这是操作归约器的专项测试，不等于 UI 帧率、保存或视频导出也提升同样倍数。批量增删、复杂布局和素材替换的开销与场景相关。

## 保存和恢复

每个项目串行处理写请求。先将完整时间线、修订号、最新事件和幂等回执写入 `commit.json`，执行文件 fsync 和原子替换；POSIX 平台还同步目录。成功提交后才更新内存并广播事件。若文件替换已成功、后续目录同步却报错，内存仍与可见提交保持一致；请求返回错误，使用同一请求 ID 重试可确认实际结果。

`timeline.json` 和 `events.jsonl` 继续保留，作为兼容文件与历史日志。若兼容文件写入失败，权威提交仍可恢复；下次写请求会先补齐待写事件。重启从权威提交恢复时间线和修订号，并补入尚未写入日志的最新事件。

日常提交、自动快照和历史恢复使用异步写盘。Windows 文件被短暂占用时采用异步等待重试，避免忙等阻塞 HTTP/SSE。小型管理文件及旧格式迁移仍保留同步读写。

`commit.json` 是工程状态的一部分，不要单独替换或删除它来导入时间线；使用正常导入、历史恢复或便携工程接口。回退旧引擎编辑时，应通过便携工程包导出、导入，避免旧版只修改兼容文件。

## 幂等请求

`POST /api/p/:pid/ops` 延续 `batchId`，AI 工具公开对应的 `requestId`：

```json
{
  "ops": [{"op":"updateOverlay","id":"title","patch":{"text":"新标题"}}],
  "actor": "ai",
  "clientId": "assistant-session",
  "batchId": "stable-logical-request-id",
  "baseRev": 12,
  "conflictPolicy": "reject"
}
```

同一项目、同一 actor 的相同请求 ID 和操作内容会返回首次结果，重启后仍生效。连接身份、标签和重试时的 baseRev 不影响幂等识别；相同 ID 配不同操作内容返回 `409 REQUEST_ID_REUSED`。

AI 工具会为一次调用创建 ID，成功结果与失败消息都会给出 requestId，传输重试复用该 ID；模型再次调用同一个逻辑请求时，应显式复用 `requestId`。预合成和重链接也在生成操作前识别重试，避免重复创建或因原对象已经移动而报错。

幂等回执按项目保留最近最多 300 项，并受约 8MB 总量限制（至少保留最新一项）。更旧的请求不保证去重。

## 字段冲突保护

历史事件新增字段路径，例如 `overlay:title/text`、`overlay:title/color`。修改同一个标题的文字和颜色可以合并；修改同一字段，或删除了对方正在修改的对象，才报告冲突。关键帧数组按动画通道作为整体字段处理。

- `conflictPolicy: "warn"`：维持兼容行为，应用修改并返回冲突列表。
- `conflictPolicy: "reject"`：发现冲突时整批不提交，返回 `409 FIELD_CONFLICT`。
- 严格模式未传 baseRev 返回 `400 REVISION_REQUIRED`；历史窗口不足返回 `409 STALE_REVISION`；超前版本返回 `409 INVALID_REVISION`。

`djian_apply_ops`、预合成和重链接工具默认使用严格模式。没有已知修订号时先读取当前时间线；发生冲突后应重新读取、理解变化并重新规划。

## 统一操作契约

`packages/engine/src/operationRegistry.ts` 集中维护操作名、公共参数 Schema、最少必填字段及系统操作标识。

- 引擎归约器使用同一份名称和必填规则。
- AI 工具参数和操作目录从注册表导出。
- `GET /api/ops` 保留原 `ops` 字段，并新增 `registry`、`parameters`。
- 复杂语义、范围清洗、素材和引用校验继续由归约器负责；注册表不是另一份渲染实现。

## 验证

测试包含不可变输入、对象引用复用、等价修改、失败回滚和 ID 释放、动态索引、局部布局；还将混合操作批次与旧的全量快照处理循环作差异比较。

持久化测试覆盖并发请求串行化、权威提交写入失败、强制终止后恢复、兼容文件落后、重启后去重，以及相同 ID 不同内容被拒绝。异步写盘测试检查文件占用重试期间计时器仍能运行。
